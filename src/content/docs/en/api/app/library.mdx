## Subscriptions

<Endpoint method="GET" path="/api/app/v1/subscriptions" auth="Token">
The library, as a delta or a full list. Limited to 120 per minute.
</Endpoint>

Query: `since` (the last `revision` you were given) and `limit` (1 to 200, default 200). The answer is `{ items, removed, revision, full }`. `removed` lists the ids of subscriptions to drop. Each item carries `kind`, `itemId`, `name`, `description`, `image`, `webUrl`, `app`, the switches `autoUpdate`, `notifyUpdates` and `paused`, `viaCollectionId` (set when a collection created it), `installable`, and `release` with the newest release's `version` and `file` (`url`, `size`, `sha256`, `name`).

Three kinds can be subscribed to, and the closed list is load-bearing: `asset`,
`mod`, `collection`. A server is not something you install; an article is not
something a device holds a copy of.

### Syncing with a revision watermark

The response carries a monotonic **revision**, which the app sends back on its
next poll. The server answers with everything changed since.

That is what lets a device poll every minute without transferring the whole
library, and what makes a subscription created in the **browser** show up on the
desktop within one poll.

A response can also declare itself **full** rather than a delta, which tells the
app it may drop anything it holds that is not in the list.

<Callout type="info" title="A subscription can point at nothing installable">
The file a subscription resolves to is **nullable**, because a subscription
outlives the release it was made against: an item whose only release is later
hidden still has a live subscription, and the app has to render it as "nothing
to install yet" rather than fail to parse the whole list.
</Callout>

<Endpoint method="POST" path="/api/app/v1/subscriptions" auth="Token">
Subscribe or unsubscribe. Limited to 60 per minute, durable.
</Endpoint>

```json
{ "kind": "mod", "itemId": 123, "subscribed": true }
```

`subscribed` is optional and toggles when it is left out. The answer is `{ subscribed, propagated, skipped }`: for a collection, `propagated` is how many item subscriptions it created (or, on unsubscribe, removed) and `skipped` how many it could not. An item that cannot be subscribed to is `400 not_installable` with a message the app can show as it is; an item that is missing or hidden is `404 not_found`.

<Endpoint method="POST" path="/api/app/v1/subscriptions/prefs" auth="Token">
Per-subscription preferences. Limited to 60 per minute, durable.
</Endpoint>

Send `kind`, `itemId` and any of the booleans `autoUpdate`, `notifyUpdates` and `paused`; the answer is `{ "ok": true }`. Preferences for an item you are not subscribed to are `404 not_found`.

Subscribing to a collection creates item subscriptions on your behalf; those
remember which collection created them, so cleanup is correct. An item can opt
out of one-click installs entirely with `subDisabled` — see
[Subscriptions](/learn/account/subscriptions).

## Installs

<Endpoint method="GET" path="/api/app/v1/installs" auth="Token">
The sandboxes on this account's machines, as `{ installs: [...] }`. An optional `appId` query narrows it to one game. Limited to 120 per minute.
</Endpoint>

<Endpoint method="POST" path="/api/app/v1/installs" auth="Token">
Create a sandbox. Answers `201` with the install. Limited to 20 per 5 minutes, durable.
</Endpoint>

`PATCH` on the same path updates one (60 per minute, durable) and `DELETE` removes it (30 per 5 minutes, durable) with `{ "deleted": true }`. The body of `POST` takes `appId`, `name` (1 to 64 characters) and optionally `description`, `gameVersion`, `loader`, `isDefault`, `strategy`, `environment` and a `launch` block of `args`, `env` and `options`. `PATCH` and `DELETE` identify the sandbox by `id` in the body; `PATCH` can also clear `description`, `gameVersion` and `loader` with `null`, and takes `playedSeconds` (up to a day) to add to the install's play time. A game the official app cannot manage is `400 app_unsupported`, more than 50 installs for one game `400 too_many`, and an install that is not yours or not there `404 not_found`.

<Endpoint method="POST" path="/api/app/v1/installs/items" auth="Token">
Add an item to an install.
</Endpoint>

The body is `installId`, `kind` (`asset`, `mod` or `collection`), `itemId`, and optionally `enabled` and `order`. `PATCH` on the same path changes `enabled` or `order` (240 per minute) and `DELETE` removes the item (120 per minute); `POST` is 120 per minute, all durable. Each answers with the whole updated install. A missing item or install is `404 not_found`, and an install holds at most 1,000 items (`400 too_many`).

An install is a game, a set of deployed items, and launch options.

### Deploy strategy

How the app puts a sandbox's files in front of the game:

| Strategy | |
| --- | --- |
| `direct` | Copies into the game folder, backing up whatever it displaced |
| `hardlink`, `symlink` | Leave the game folder made of pointers |
| `usvfs` | Runtime API hooking — declared, not yet implemented |

The server accepts `direct`, `hardlink`, `symlink` and `usvfs` and defaults to `hardlink`; a value it does not recognise is **not fatal to the app** — it falls back to its
own default. That is what lets a new strategy ship in the app before it ships
here.

### Environment

`client`, `server` or `shared` (default `client`). Not decoration: it decides which mods are
offered for the sandbox and which of the game's own options are shown. A
dedicated server and a player's game are the same files arranged differently,
and a manager that cannot tell them apart offers everybody both halves of every
list.

`shared` accepts both, which is what a mod's `ALL` environment means.

### Launch options

Every field optional, every one with a "leave it alone" meaning. They are `graphics` (`default`, `low`, `medium`, `high`, `ultra`), `windowMode` (`default`, `windowed`, `borderless`, `fullscreen`), `width`, `height`, `monitor`, `fpsLimit` (0 for none), `vsync`, `memoryMb`, `hideOnLaunch` and `confirmUpdates`, each range-checked, next to `launch.args` (up to 64) and `launch.env`. The
overwhelmingly common install overrides nothing, and a launcher that silently
forces 1920×1080 on somebody who never asked is worse than one with no settings
at all.

What each key **means** for a given game is decided by that game's launch
plugin, not by this API.

## Downloads

<Endpoint method="GET" path="/api/app/v1/downloads" auth="Token">
What each of this user's devices is downloading, as `{ devices: [...] }`, most recently heard from first and at most 25. Each device has a `deviceName`, `isThisDevice`, the counts `active`, `queued`, `paused`, `failed` and `finished`, `speedBps`, `remainingBytes`, up to 25 `items` (`id`, `label`, `status`, `done`, `total`, `speedBps`) and `updatedAt`. Limited to 120 per minute.
</Endpoint>

<Endpoint method="POST" path="/api/app/v1/downloads" auth="Token">
The app reports its queue (answers `{ "ok": true }`). Limited to 600 per 5 minutes.
</Endpoint>

The row is keyed on the token, so two machines are two rows and signing one out deletes its row. A session that is not tied to a device is `400 no_device`, and a device that has since been signed out `401 no_device`. `DELETE` on the same path clears the account's rows (`{ "cleared": true }`, 60 per 5 minutes).

Somebody starts a 40 GB modpack on their desktop and then wants to know, from
their phone, whether it has finished. There is no other way to answer that: the
app is the only thing that knows, and it is not reachable from outside the
machine it runs on. So it reports, and this holds the last thing it said.

<Callout type="warning" title="This is a display snapshot, not a queue">
It never drives a download. The queue lives on the device and is the authority
for everything; this is overwritten on every report and safe to lose.
</Callout>

Note what a download row does **not** carry: no URL, no filesystem path, no
device identifier beyond the user's own label for the machine. A path would put
somebody's username and drive layout into a row.
