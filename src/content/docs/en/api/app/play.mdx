## The app catalogue

<Endpoint method="GET" path="/api/app/v1/apps">
Every game, engine and VoIP platform the site tracks. Authentication is
**optional**.
</Endpoint>

The app's front door. The website has nothing equivalent, because its chrome is
built around one chosen game; the app opens on a flat list across all of them,
so it needs the list itself.

Nothing here is account-scoped — it is the same public catalogue an anonymous
visitor reads a page at a time on the site. A bearer token is *accepted* so the
rate limit is charged per account rather than per address, which matters for a
household behind one address.

Takes `search` (up to 120 characters), `ids` and `slugs` (up to 100 each), `type` (`GAME`, `GAME_SINGLEPLAYER`, `GAME_ENGINE`, `VOIP` or `OTHER`), `playable`, `managed`, `installable`, `sort` (`players` by default, or `servers`, `content`, `name`), `cursor` and `limit` (1 to 100, default 50). The answer is `{ apps, nextCursor, total, playEnabled }`. Limited to 120 per minute.

`installable=true` narrows the list to the games this app could actually put on
disk, so a launcher does not draw an install button it will then have to
retract. Where that build *is* comes from a second request — see
[`/apps/:id/build`](/learn/api/app/releases#where-is-this-games-build).

<Callout type="info" title="`playEnabled` is answered even when it is false">
The play centre is a setting an operator can switch off. An app that could not
tell "switched off" from "no game here is playable" would draw a catalogue that
silently lost every Play button, and give the user nothing to read about it.
</Callout>

## Resolving a launch

<Endpoint method="POST" path="/api/app/v1/play/launch">
One launch, resolved. Authentication is **optional** — nothing here discloses
anything a signed-out visitor could not already read.
</Endpoint>

The same handoff the website's own player performs, on the app's transport.
Every decision is made server-side and the client is told the answer. The body is `appId`, `mode` (`web` or `app`), and optionally `serverId`, `locale` (default `en`), `options` and `build` (a build name, letters, digits and `._-`). The answer is `data: null` when it is not available from here; otherwise for `web` it is `{ mode, loaderUrl, boot }`, where `boot` is the descriptor the game loader reads (including a single-use handoff code when the member is signed in), and for `app` it is `{ mode, uri, solo }`, the `tmc://` link to hand the installed app. A `build` the game does not offer is refused, unlike everything else here, with `400 build_unsupported` or another `400 build_…` code naming why, because a silent substitute would be a different build than the one a bug report is about. Limited to 120 per 5 minutes.

<Params>
  <Param name="null means &quot;not from here&quot;">
    The app is hidden, the feature is off, the mode is not available, the named
    server belongs to a different game, or direct play is off and no server was
    chosen. **One vocabulary for all of them** — naming which would tell a
    caller which column to probe, and none of them changes what the app does
    with the answer.
  </Param>
  <Param name="Option values are coerced against the app's own declaration">
    They arrive from a device, so an unknown key is dropped, a wrong type falls
    back to the app's default, and an integer is clamped into the declared band.
    Without that, an option is an unvalidated string interpolated into a URI
    handed to a native client.
  </Param>
  <Param name="Direct play is enforced, not merely hidden">
    The app draws no Play button without it — but a deep link and a mismatched
    server both reach this code without passing one, and the second would
    otherwise degrade into exactly the serverless launch the flag forbids,
    silently.
  </Param>
</Params>

A server's address is gated on its own `showNetInfo`, by the same helper the
server page uses.

## The play centre lists

<Endpoint method="GET" path="/api/app/v1/play/page">
The play centre's page: games, servers, lobbies or invites. Authentication is **optional**; a token adds the viewer's party. Limited to 240 per 5 minutes.
</Endpoint>

Query: `tab` (`games`, `servers`, `lobbies` or `invites`), `q` (up to 120 characters), `appId`, `mode`, `sort` (`players`, `recent`, `name`, `servers`, `popular`, `trending` or `newest`), `populated`, `joinable` and `cursor` (an offset, not an opaque string). The answer is `{ tab, apps, servers, lobbies, nextCursor, anyPlayable, party, totals }` and is `null` when the play centre is switched off. Rows carry only what a card draws; a server row has `curUsers`, `maxUsers`, `map` and, when the owner shows it, `host` and `port`.

<Endpoint method="GET" path="/api/app/v1/play/playable">
Which games can be played, so a button is drawn only where it will work. Authentication is **optional**. Limited to 240 per 5 minutes.
</Endpoint>

The answer is `{ enabled, appIds, directIds, soloIds }`: the games playable at all, the ones that can be joined with no server chosen, and the ones that run solo.

<Endpoint method="POST" path="/api/app/v1/play/quick-match">
Rank a game's servers and pick one. Authentication is **optional**, because nothing in the ranking is relative to the viewer. Limited to 60 per 5 minutes.
</Endpoint>

The body is `{ "appId": 12, "rotation": false }`. The answer is `null` when play is off, or `{ appName, country, rotation, scanned, full, stale, rotationHits, top, best, tookMs }`, where `best` is a server row and `top` the ranked candidates with a `score` and the reasons (`why`) for it.

## Finding a server from a link

<Endpoint method="GET" path="/api/app/v1/servers/lookup?host=&port=">
Which listed server is at that address. Authentication is **optional**. The answer is `{ servers }`, at most 10 browser rows.
</Endpoint>

What the app calls when it is handed a `tmc://play/<host>:<port>` link. The
rows that come back are the public catalogue — the same ones the browser
already publishes — so answering discloses nothing new, and a **delisted server
is still found**, because a player following a link to one should be told what
it is rather than shown nothing.

<Params>
  <Param name="host" type="string" required>
    Hostname or IP literal, unbracketed, up to 255 characters. The app strips the brackets off an
    IPv6 address before it asks.
  </Param>
  <Param name="port" type="number">
    Optional (1 to 65535), because `tmc://play/example.com` is a legitimate link. Absent
    matches any port on that host, and a host running two servers answers with
    both — which the app renders as a choice rather than guessing.
  </Param>
</Params>

<Callout type="info" title="The rate limit here is much tighter than `/browse`">
Thirty a minute. A person follows one link at a time, so a ceiling this low
only bites a client with a broken retry — and it is also what stops the
endpoint being walked as an address oracle.
</Callout>

## The scoped player key

<Endpoint method="POST" path="/api/app/v1/play/scope-key" auth="Token">
The caller's identifier on one server.
</Endpoint>

```json
{ "scope": "server:412" }
```

The answer is `{ "scope": "server:412", "key": "…" }`. A game session may call this one, and it is limited to 30 per minute because each key writes a row. A player's client asks for this on its way into a game and hands the answer to
the server, which is then able to read and write that player's avatar — and file
their statistics — **without ever learning their account id**. See [the
derivation](/learn/api/integration/avatars#the-player-key).

<Callout type="warning" title="A key is an identifier, not a proof">
Anybody who has one can name it, and a client could hand a server a key it was
given by another player. What that buys is **wearing somebody else's outfit**,
because the endpoints behind it are scoped to the server's own credential — a
stolen key reads an avatar the thief could see by standing next to its owner.

Where a server needs the player to have *proven* who they are, that is what
`dot-auth`'s connect tickets are for, and the key rides inside the ticket
instead of being asked for here.
</Callout>

**The scope is whatever the caller says**, and it has to be: the client is
joining a server whose name only it knows, and the derivation's guarantee is
that *different* scopes cannot be correlated — not that any particular scope is
off limits. A player asking for `global` is opting into being recognised
everywhere, which is theirs to choose.

A scope is letters, digits and `_ . : -`, up to 64 characters; anything else is `400 bad_request`.

## The player's own avatar

<Endpoint method="GET" path="/api/app/v1/avatar" auth="Token">
The caller's own avatar document. A game session may read it (60 per minute).
</Endpoint>

<Endpoint method="PUT" path="/api/app/v1/avatar" auth="Token">
Save it. A game session is refused: an avatar is authored on the site, and a loader that could publish one could quietly replace a member's appearance everywhere it is shown. Limited to 20 per minute.
</Endpoint>

Both answer `404 not_found` when avatars are switched off on the site. A document the avatar code refuses is a `409` whose `code` is the reason.

The same documents [the integration
endpoints](/learn/api/integration/avatars) move, addressed as "me" and
authenticated by the player's own token rather than by a server credential. This
is what a game with its own in-game avatar editor calls, and what the desktop
app calls to draw the figure on its profile screen.

**There is deliberately no scoped key in this address.** The scoping exists so a
*server* cannot correlate a player across the platform; a player asking about
themselves has nothing to be protected from, and requiring them to derive their
own key first would be ceremony with no property behind it.

A publish here is exactly as authoritative as one from the site's own editor —
it is the member acting for themselves — so it goes through the same code, and a
document naming another schema is refused for the same reason.

## The cross-origin half

A game running **in the browser** is third-party code on its own origin — that
iframe boundary is the point, not an accident of hosting — so the handful of
routes it needs answer a preflight and are callable from it: `auth/handoff`,
`auth/refresh`, `auth/revoke`, `me`, `play/scope-key`, `avatar`, the four
[statistics](/learn/api/integration/stats#self-reported-figures) routes and the two workshop routes. All of them accept a game session, with two limits: `me` and `avatar` only for reading, and the token routes only for its own session. Every other route refuses one with `403 wrong_credential`.

Nothing else on the app API does. The rest is one installed client talking to
us, and has no reason to be reachable from a web page.

A web player's credential is also **not a device token** — see [the handoff
flow](/learn/api/app/auth#the-web-player-handoff).
