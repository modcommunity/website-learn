The app signs in with a **device flow**: it opens a login, shows the user a
code, and polls until they approve it in a browser.

## 1. Open a login

<Endpoint method="POST" path="/api/app/v1/auth/device">
Unauthenticated by necessity — the app has no credentials at this point.
</Endpoint>

```json
{
  "client": { "name": "TMC Desktop", "platform": "windows", "version": "1.4.0" },
  "codeChallenge": "<PKCE S256 challenge, base64url>"
}
```

```json
{
  "deviceCode": "…",
  "userCode": "…",
  "verificationUri": "https://moddingcommunity.com/login/device",
  "verificationUriComplete": "https://moddingcommunity.com/login/device?code=…",
  "expiresIn": 600,
  "interval": 5
}
```

The client info is **self-reported and untrusted** — it is a label for the
approval screen, nothing more. `codeChallenge` is 43 to 128 characters. `expiresIn` is in seconds and `interval` is the polling gap the app should keep.

`verificationUriComplete` is what the app actually opens; `verificationUri` is
where the user goes when the code has to be typed.

What bounds this endpoint is its rate limit (10/minute, counted **durably**
because this is the front door) and the grant's own 10-minute lifetime: a flood
of starts creates a flood of rows that expire on their own and that nobody can
approve.

## 2. Poll

<Endpoint method="POST" path="/api/app/v1/auth/token">
Returns the credential pair exactly once, on the first call after approval.
</Endpoint>

```json
{ "deviceCode": "…", "codeVerifier": "<PKCE verifier>" }
```

Every other outcome is an error envelope whose `code` the app branches on:

| `code` | Status | Means |
| --- | :-: | --- |
| `authorization_pending` | **202** | Waiting for the human. Not a failure |
| `slow_down` | **202** | Polling too quickly |
| `access_denied` | 400 | The device was not approved |
| `expired_token` | 400 | The attempt expired. Start again |

`expired_token` is deliberately the answer to **several** different things: an unknown or expired device code, a grant already claimed, too many polls against one grant, and a wrong PKCE verifier. A wrong verifier is never a user mistake (the verifier never leaves the app that made it), so it means someone else holds the device code and the grant is deleted rather than left to be guessed against. `deviceCode` is 8 to 128 characters and `codeVerifier` 43 to 128. A poll that loses the race to claim a grant gets `slow_down`.

<Callout type="info" title="Pending and slow-down are 202, not 4xx">
Waiting on a human is not a client error. Naming them as codes keeps the app
from having to guess from a status code.
</Callout>

On success:

```json
{
  "accessToken": "…",
  "refreshToken": "…",
  "expiresIn": 3600,
  "user": { "id": "…", "name": "…", "username": "…", "avatar": "…", "role": "…" }
}
```

### Two rules that make polling safe

<Params>
  <Param name="The grant is consumed atomically">
    Redemption is a conditional update from *approved* to *claimed*; only the
    update that actually changed a row mints a token. Two concurrent polls
    therefore cannot both succeed — not a theoretical race, since the app polls
    on a timer **and** on a deep-link wake.
  </Param>
  <Param name="PKCE is checked before anything is minted">
    A device code alone is inert, so one read off a screen or scraped from a log
    buys nothing.
  </Param>
</Params>

## 3. Refresh

<Endpoint method="POST" path="/api/app/v1/auth/refresh">
Rotate the credential pair.
</Endpoint>

Unauthenticated in the bearer sense: **the refresh token is the credential**, and
requiring a live access token alongside it would make refresh impossible in the
one situation it exists for. The limit is 30 per minute, durable.

```json
{ "refreshToken": "…" }
```

The answer has the same shape as a successful poll: `accessToken`, `refreshToken`, `expiresIn` and `user`. The old refresh token is retired by the rotation. Failures are `401`: `invalid_grant` for an unknown, expired or revoked token (and for an account that no longer exists), and `token_reuse` for a retired one coming back. The route accepts cross-origin calls, because a game session rotates its own pair from its own origin.

<Callout type="warning" title="Reuse signs every device out">
A retired refresh token coming back is reported as its own code, because it
means something specific: the whole lineage is revoked and every device is
signed out. The app shows that as a security notice rather than a generic
"please sign in".
</Callout>

## 4. Revoke

<Endpoint method="POST" path="/api/app/v1/auth/revoke" auth="Token">
Sign this device out.
</Endpoint>

Revokes the **whole lineage** rather than the presented pair, so a sign-out is
final: a refresh token the app still holds in its keychain cannot resurrect the
session after the user asked for it to end. The body is ignored (send `{}`), the answer is `{ "revoked": true }`, and the limit is 20 per minute.

A game session may call it too: the lineage is the one the caller presented, so a loader tidying up after itself ends its own session and never signs the member out of their devices.

## The web player handoff

<Endpoint method="POST" path="/api/app/v1/auth/handoff">
Turn a web-player handoff code into a game session. Unauthenticated in the
bearer sense — **the code is the credential.**
</Endpoint>

This is the endpoint that ends "sign in again, inside the canvas". A member
already signed into the site presses Play, the boot descriptor carries a
single-use code, and the game's loader posts it here to get a credential for the
player it is about to seat.

```json
{ "code": "…", "client": { "name": "…", "platform": "web", "version": "1" } }
```

`client` is optional and untrusted, a label for the member's device list; it defaults to "Web game player" on the `web` platform. The answer is the poll's success shape plus `appId` and `serverId`, echoed so a loader that serves several games from one bundle can check it got what it asked for. A code that is unknown, expired, already spent or whose account has gone is one `400 invalid_grant`, so the route cannot be used to test whether a code was ever real. The route accepts cross-origin calls, since the game runs on its own origin.

What bounds it is what the code *is*: one use, sixty seconds, one member, one
app — plus a durable rate limit, because it mints credentials and a cache outage
must not turn it into an unmetered one.

<Callout type="warning" title="What it mints is deliberately not a device token">
The redeemer is a loader the app's operator uploaded, running on our origin —
code we did not review. So the pair returned here is a **game** credential,
bound to the app the code was minted for, and **every route refuses it unless it
has explicitly opted in**.

A member's installs, subscriptions, reviews and profile are all on the other
side of that line. What a game token can do is learn who is playing, read that
player's own avatar (it cannot publish one), and file their
[statistics](/learn/api/integration/stats#self-reported-figures).
</Callout>

A game session is bound to one app, so an `app` it does not agree with in a body
is **refused rather than obeyed**.

## Identity

<Endpoint method="GET" path="/api/app/v1/me" auth="Token">
Identity plus the settings that sync. A game session may call this one; it is how a loader learns who is playing.
</Endpoint>

```json
{ "user": { "id": "…", "name": "…", "username": "…", "avatar": "…", "role": "…" }, "settings": { }, "serverTime": 1790000000 }
```

`serverTime` is the server's clock in whole seconds, so the app can notice a badly skewed device. The limit is 120 per minute.

<Endpoint method="PATCH" path="/api/app/v1/me" auth="Token">
Write the synced settings.
</Endpoint>

The body is a partial of the `settings` object, so two devices editing different toggles do not overwrite each other, and the answer is the full settings object. A game session is refused. The limit is 30 per minute, durable.

`settings` holds `timezone` and `locale` (short strings), `emailNotifications` and `pushNotifications`, and one boolean per notification topic: `notifySystem`, `notifyComments`, `notifyReviews`, `notifyReleases`, `notifyMentions`, `notifyModeration`, `notifyCredits`, `notifyFriends`, `notifyFollowers`, `notifyMessages`, `notifyStatus`, `notifyParties` and `notifyGroups`.

The app calls this on every launch. It is also how a **stale access token is
discovered**: a `token_expired` here triggers one refresh-and-retry before the
user is shown a signed-out state.

The settings it carries are deliberately a subset of your account settings —
ones that only mean something in a browser, or that the app has no interface
for, would become dead fields the app is nonetheless responsible for
round-tripping correctly. Everything in it is a plain boolean or a short string,
so an update is a partial of exactly that shape.
