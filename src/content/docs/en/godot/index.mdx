**Dot** is The Modding Community's collection of Godot 4 assets: twenty-two
addons, a shell launcher, a server tool and five games that exist to run the
addons together. They are on the site as the [Dot assets
collection](/co/4-dot-assets) and on GitHub under
[`modcommunity`](https://github.com/modcommunity).

They add the parts of a game platform that are not engine features — accounts,
avatars, content delivery, netcode, dedicated servers, moderation, timers,
leaderboards — as **layers above stock Godot**. A game that wants none of it
stays an ordinary Godot project.

<Callout type="warning" title="Treat this as partially tested">
Every asset has its own headless test suite and those suites pass, but very
little of this has been in front of real players yet. Expect rough edges, and
report anything you hit. The collection was built with Claude Code and is
maintained the same way — that is stated up front in every repository's README
rather than buried.
</Callout>

## We are not forking Godot

Worth settling first, because "a fork of Godot" and "addons for Godot" lead to
different projects and only one of them is finishable.

A fork means owning the engine's release cadence, its export templates for six
platforms, its web build, and every rebase for ever — and the moment it
diverges, a game written for it cannot use anything from the Godot asset
library. The parts of a platform people actually mean are not engine features:
identity, avatars, content delivery, dedicated servers, moderation, discovery.
Every one of those is a layer *above* an engine.

So: **stock Godot, plus addons, plus one open backend protocol.**

## Only `dot-core` is ever a hard dependency

This is the rule the whole collection is built around, and in GDScript it is not
merely a preference: **a script that so much as *mentions* a `class_name` the
project does not have fails to parse**, and takes every script that references
it down with it. An addon that imported another would make that other addon
mandatory for everyone.

So everything else is discovered at runtime, duck-typed, or bridged by the game:

- `dot-server` finds `dot-auth` and `dot-cloud` through
  [`DotRegistry`](/learn/godot/conventions#dotregistry-instead-of-autoloads) and
  imports neither.
- `dot-net` needs only `dot-core` and moves bytes through a `Callable`.
- `dot-fps-controller`, `dot-combat`, `dot-loadout`, `dot-match` and `dot-2d`
  each ship a `*NetSync` class that describes what to replicate **as data** —
  property names and type names as *strings* — which a bridge resolves with
  `DotNetVar.Type[spec.type]`. None of them names a `dot-net` identifier.
- `dot-combat` takes lag compensation as two `Callable`s.
- `dot-ui` names nothing outside `dot-core`: its feed takes coloured fragments
  and its table takes rows of dictionaries.
- `dot-user` and `dot-user-avatar` do not import each other, and `dot-loadout`
  carries its own copy of a storage-key check for the same reason.

<Callout type="info" title="Duplication here is deliberate">
Where two addons hold the same twenty lines, that is the rule above being paid
for, not an oversight. Deduplicating it into a shared import is how one addon
becomes a dependency of another.
</Callout>

## How the pieces stack

```
                        ┌──────────────┐
                        │   dot-core   │  logging, capabilities, paths,
                        │              │  node refs, config, jobs,
                        └──────┬───────┘  transports, HTTP
      ┌───────────┬────────────┼────────────┬───────────┬──────────┐
      ▼           ▼            ▼            ▼           ▼          ▼
┌───────────┐ ┌──────────┐ ┌─────────┐ ┌──────────┐ ┌────────┐ ┌────────┐
│ dot-cloud │ │ dot-auth │ │ dot-net │ │dot-server│ │ dot-ui │ │ dot-2d │
└─────┬─────┘ └────┬─────┘ └─────────┘ └────┬─────┘ └────────┘ └────────┘
      │            │                        │
┌─────┴─────┐ ┌────┴───────────┐    ┌───────┴────────┐
│ dot-user  │ │dot-user-avatar │    │  dot-platform  │
└───────────┘ └────────────────┘    └────────────────┘

      ┌──────────────────┬──────────────┬─────────────┐
      ▼                  ▼              ▼             ▼
┌────────────┐    ┌────────────┐  ┌───────────┐ ┌──────────────────┐
│ dot-combat │    │dot-loadout │  │ dot-match │ │dot-fps-controller│
└────────────┘    └────────────┘  └───────────┘ └──────────────────┘
      └──────────────────┴──────────────┴─────────────┘
                               │  every one of these needs
                               ▼  ONLY dot-core
                    ┌──────────────────────┐
                    │   your game          │  the bridges live here
                    └──────────────────────┘
```

The arrows are *optional* relationships everywhere except the top row. Read them
as "works better with", not "requires".

## The three groups

**The platform half** — `dot-core`, `dot-cloud`, `dot-auth`, `dot-net`,
`dot-server`, `dot-user`, `dot-user-avatar`, `dot-platform`. Who a player is,
what they look like, how they get content, and the dedicated server they connect
to.

**The gameplay half** — `dot-fps-controller`, `dot-2d`, `dot-combat`,
`dot-loadout`, `dot-match`, `dot-ui`. Movement, weapons, equipment, the match
loop and the interface. Each needs only `dot-core`.

**The genre kit** — `dot-timer`, `dot-map`, `dot-props`, `dot-leaderboard`,
`dot-stats`, `dot-voice`, `dot-moderation`, `dot-vote`. Everything a person
needs to *run a server* people come back to: a records table, a map rotation, a
vote for what plays next, punishments that outlive a session.

## The genre kit is a strategy, not a feature list

The collection's problem was never that it lacked features. It is that **nobody
has a reason to be the first person on a new platform**, and a general-purpose
addon family does not supply one. A genre does.

The one chosen is surf and bunny-hop — Counter-Strike's movement community,
still running Source servers on a timer plugin written for an SDK last opened in
2013. It is a good first genre for four reasons and only the fourth is about us:

1. **Movement is the hardest thing to get right.** Almost nobody reproduces
   Quake acceleration and Source's `TryPlayerMove` closely enough that a player
   who has surfed for ten years does not feel the difference.
2. **It is server-shaped.** A surf community *is* a server: a rotation, a
   records table, an admin who zones new maps, regulars who care about the
   leaderboard.
3. **Its content is portable and community-made.** Maps come from mappers, zones
   come from admins, and both are traded as files.
4. **It is small enough to finish.** Four addons and a playable game.

## Everything is MIT, except the backend

The addons, the games and the tooling are MIT licensed and open source. The one
thing that is not is the **web back-end infrastructure** — TMC's own deployment.
Every addon that talks to it does so over a documented HTTP protocol, and points
at a `backbone_url` you can change, so a project that wants its own backend
builds one and changes a setting.
