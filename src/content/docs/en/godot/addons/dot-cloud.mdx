A server hands a client a manifest; the client downloads what it is missing,
verifies it, and mounts it — on Windows, macOS, Linux, Android, iOS and in the
browser.

Requires `dot-core`.

```gdscript
var cloud := DotCloudClient.new()
add_child(cloud)

cloud.config = DotCloudConfig.new()
cloud.config.trusted_keys = {"default": PUBLIC_KEY_PEM}
await cloud.start()

cloud.phase_changed.connect(func(_p, text): status_label.text = text)
cloud.progress_changed.connect(func(p): bar.value = p.fraction * 100.0)

var res := await cloud.acquire("https://cdn.example.com/dm_arena/manifest.json")
if res.ok:
    get_tree().change_scene_to_file(res.value)
```

Publishing is a headless CLI that produces a **static directory** — a
`manifest.json` plus an `objects/` tree — that any web server or CDN hosts with
no configuration:

```bash
godot --headless --path . --script addons/dot_cloud/publish/dot_cloud_cli.gd -- \
    keygen --private keys/content.key --public keys/content.pub

godot --headless --path . --script addons/dot_cloud/publish/dot_cloud_cli.gd -- \
    publish --source content/dm_arena --out dist/dm_arena \
    --id dm_arena --version 1.2.0 --entry arena.tscn --key keys/content.key
```

## The two constraints that shaped everything

**Godot cannot unmount a resource pack.** Not slowly, not with a workaround —
the API does not exist. So every content set gets its own versioned path,
`res://<root>/<content_id>/<version>/`, and nothing ever needs replacing.
"Unloading" means dropping references, not reclaiming the file table. That one
fact is why swapping games at run time works at all.

**Unsigned content is remote code execution.** A Godot pack can contain scripts,
so a manifest decides what gets executed. `require_signed_manifests` defaults to
on and the config refuses to validate without a trusted key. You can turn it off
for a LAN or a first-party server; it warns every time.

## What it does

- **Content-addressed cache.** Files are stored under their SHA-256, so two
  games sharing an asset download it once and republishing re-downloads only
  what changed.
- **Resumable parallel downloads.** Mirror failover, HTTP range resume, a
  circuit breaker per source, bandwidth throttling, honest progress and ETA.
- **Three sources.** HTTP/CDN, a local directory (development, LAN, bundled
  content), and in-band over the game connection for a server with no web host.
- **Quota awareness.** Browser storage estimates, mobile ceilings, and
  least-recently-used eviction that never evicts content currently in use.

## What mounting checks

Between download and mount, a pack is held to four rules that each came from a
failure somebody measured:

- **Its `requires.json` is read first.** A pack's scripts compile against the
  host's addons, so one needing a newer addon used to fail to parse mid-load.
  Now it is refused before a script loads, with *"This game needs dot-net API
  level 3 or newer; this client has level 2."* — see
  [addon API levels](/learn/godot/addons/dot-core#addon-api-levels-dotaddonapi).
  `host_role` names the side.
- **A content id may name its owner: `<owner>/<name>`.** `/` cannot occur in
  either half, so a key scoped `alice/*` is exact — a flattened `alice_bob`
  could not tell `alice` + `bob_x` from `alice_bob` + `x`. Each segment must be
  a slug; a bare id, which every first-party pack is, still validates.
- **One id cannot mean two things.** A second manifest for the same
  `content_id@version` from a different publisher is refused with
  `CODE_CONFLICT` rather than handed the first one's mount — a pack can contain
  scripts, and "the first one's" is somebody else's code. An equal manifest
  re-read off the wire is still a cheap no-op.
- **A mounted pack registers its own uids, and may not take anybody else's.**
  An imported asset (a `.glb`, a `.png`) refers to its siblings by UID, which
  does not survive being mounted elsewhere; the mounter points each UID at the
  mounted copy. A UID the host already holds is refused and reported, or every
  `load("uid://…")` in the build could be re-pointed at downloaded content.

<Callout type="warning" title="Imported outputs ship under `_imported/`, never `.godot/`">
A published pack carries the engine's imported outputs, and they used to sit at
their real path, `.godot/imported/`. Linux reads that back perfectly; **a web
export cannot**, and the whole game refused to start in the browser. Outputs now
ship under `_imported/`, with each `.import` marker rewritten to name where the
output landed. Missing art in a mounted pack otherwise shows up only as
warnings — the pack verifies, mounts and loads with its textures absent.
</Callout>

## Where a game plugs in

<Params>
  <Param name="DotCloudSource subclass">
    `source_name()`, `is_supported()`, `can_serve(manifest)`, `fetch(...)`.
    Three ship — `DotCloudSourceHttp`, `DotCloudSourceLocal`,
    `DotCloudSourceNetchan` — and a fourth is yours: a torrent, a
    platform-specific CDN, a signed S3 URL minter.

    A `fetch` **must** write to `DotCloudStore.partial_path` for the file's
    hash, resume from `partial_size` where it can, and finish through
    `commit_partial`. That is the only place the hash is verified, and writing
    into the object directory directly is exactly how unverified content gets
    mounted.
  </Param>
  <Param name="can_serve() vs is_supported()">
    The distinction earns its keep. A source can be perfectly healthy and still
    have no way to reach *this* manifest — an HTTP source with no `base_urls`
    against a manifest carrying no mirrors. Returning a failure from `can_serve`
    means "skip me for this manifest, and say why", and is **not** recorded
    against the circuit breaker.
  </Param>
  <Param name="priority" type="int">
    On every source. Lower runs first; the in-band fallback deliberately sits
    last.
  </Param>
  <Param name="DotCloudConfig">
    `trusted_keys`, `require_signed_manifests`, `cache_bytes`,
    `mobile_cache_bytes`, `web_quota_fraction`, `parallel_downloads`,
    `max_attempts_per_file`, `throttle_bytes_per_sec`, `mount_root`,
    `verify_before_mount`, `resume_downloads`. Layered like every `DotConfig`.
  </Param>
  <Param name="Signals">
    `phase_changed`, `progress_changed`, `file_finished`, `sync_finished`,
    `content_ready`, `content_released`, `failed`.
  </Param>
</Params>

## The content interface other addons expect

Register a `DotCloudClient` and it publishes itself under `dot_cloud_client`.
`dot-map`'s loader and `dot-server`'s game change both reach it through that
name and call:

```gdscript
ensure(content_id: String, version: String) -> DotResult
is_mounted(content_id: String, version: String) -> bool
```

Most addons reach them through `DotContent` in
[`dot-core`](/learn/godot/addons/dot-core#downloadable-content-dotcontent), the
one shared caller — which is how avatar parts, props, NPCs, vehicles and items
that name content now actually fetch it.

<Callout type="warning" title="An absent cloud client is a legitimate configuration">
Every call site treats "no `dot_cloud_client`" as "this deployment ships its
content inside the build" — which is true for most of them, and is therefore
indistinguishable from a client that failed to register. When a delivered map or
a delivered game silently does nothing, check the registry first.
</Callout>
