Spawnable props, the limits that keep a server alive, and the tools that move
them.

Requires `dot-core`.

## Server-authoritative, and not predicted

Rigid-body physics is not reproducible across machines — the solver's iteration
order and the last bits of every float differ — so a predicted prop is a prop
that is corrected constantly. **The server owns every prop; the client draws
what it is told; the tools send intent.**

```gdscript
var spawner := DotPropSpawner.new()
spawner.authoritative = true                  # on the server only
spawner.catalogue = DotPropCatalogue.load_json("res://props.json").value
spawner.limits = DotPropLimits.new()
spawner.world_ref = DotNodeRef.of_path(^"../World")
add_child(spawner)

spawner.refused.connect(func(player, prop, reason): tell(player, reason))

spawner.advance(delta)
spawner.spawn(&"crate", player_id, aim_point, Basis.IDENTITY)
```

```json
{
  "format": 1,
  "props": [
    {"id": "crate", "name": "Crate", "category": "props",
     "scene": "res://props/crate.tscn", "mass": 20},
    {"id": "safe", "category": "props",
     "scene": "res://props/safe.tscn", "mass": 900, "cost": 8},
    {"id": "pillar", "category": "scenery",
     "scene": "res://props/pillar.tscn", "can_grab": false}
  ]
}
```

## The tools

```gdscript
var gun := DotPhysGun.new()
gun.spawner = spawner
gun.wielder = player_id

gun.grab(space_state, eye_position, aim_direction, view_basis)
gun.hold(eye_position, aim_direction, view_basis, delta)   # every physics tick
gun.push(scroll_amount, delta)
gun.release()
gun.freeze_held()
```

```gdscript
var grav := DotGravGun.new()
grav.pull(space_state, eye_position, aim_direction)
grav.carry(eye_position, aim_direction, delta)
grav.punt(space_state, eye_position, aim_direction)
```

The physics gun holds with a **spring**, not a transform: setting a transform on
a rigid body fights the solver and produces a prop that jitters and shoves
everything it touches.

## Breaking a prop, and standing on one

`DotPropDamage` holds hit points for props and applies damage to nobody. The numbers live on `DotPropDef` — `max_health` and `break_impact_speed` — so a definition stays checkable without loading its scene; the state is keyed by instance id, so a breakable prop is still a plain scene with a `RigidBody3D` at its root. `break_impact_speed` is a speed rather than damage, because a crate has to survive being walked into and must not survive a bus. `max_health = 0` is indestructible, since every prop written before the field decodes to zero. When something explodes it describes the blast and shoves other props; what that does to a person is [dot-combat](/learn/godot/addons/dot-combat)'s. Signals: `damaged`, `broken`, `exploded`.

`DotPropCarry` is what makes a crate an object rather than scenery: a character motor sweeps a shape and slides, so without it a crate is exactly as solid and as immovable as the floor. `stand()` presses a player's weight into the prop under them, `ride()` carries them with it — angular velocity included, or a player on a spinning crate drifts toward the middle — and `push()` shoves one. It reads the motor's `ground_id`, which is a local handle and deliberately not part of the simulation.

## Where a game plugs in

<Params>
  <Param name="DotPropCatalogue / DotPropDef">
    What can be spawned. Id, name, category, scene, mass, cost, `can_grab`,
    health, and a `meta` dictionary. A delivered prop carries a `content_id`,
    and `ensure_content()` fetches the packs the catalogue's props live in.
  </Param>
  <Param name="DotPropDef.meta.script" type="a PATH">
    A prop that has code. **A path, not a `class_name`** — a mounted `.pck`
    cannot register `class_name` globals, so a path is the only shape a
    delivered prop can take. See
    [game-playground](/learn/godot/games#game-playground).
  </Param>
  <Param name="DotPropLimits">
    Per-player counts, per-player frozen counts, a spawn cooldown, an undo
    depth, a total cap, and grab mass limits. Each one is defending against a
    specific way a sandbox server dies.
  </Param>
  <Param name="DotPropTool subclass">
    `effective_reach`, `target`, `may_act_on`. A new sandbox tool, or a weapon.
    `DotPhysGun` and `DotGravGun` are the shipped ones.
  </Param>
  <Param name="Signals">
    `spawned`, `removed`, `refused` on the spawner; `grabbed`, `released`,
    `freeze_changed` on `DotPhysGun`.
  </Param>
</Params>

<Callout type="warning" title="Ownership and undo are two lists">
When they were one, trimming it to the undo depth removed props from their
owner's *account* as well as their history — so a player could hold `undo_depth`
props against their budget and any number beyond it for free, and
`clear_player` left the rest in the world.
</Callout>

<Callout type="warning" title="`DotPropDef.mass` has to reach the body">
A catalogue saying 900 kg over a scene saved at 20 kg gives a prop a physics gun
refuses for being too heavy and a gravity gun throws like a beach ball. It shows
the moment a game ships one scene for a dozen props, which is the cheap way to
do it.
</Callout>
