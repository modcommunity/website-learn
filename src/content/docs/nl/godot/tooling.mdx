[`dot-server`](/learn/godot/addons/dot-server) is diep instelbaar — cvars, flags,
`server.cfg`, `autoexec.cfg`, `+command`-argumenten, RCON, en gelaagde
configuratie uit bestand, omgeving en argv. Wat ontbrak was een voordeur. Dit is
de deurbel.

## `dotserve`

Het enige stuk van de collectie dat geen Godot-add-on is: een shellscript dat
`bash` en een Godot 4.7+-binary nodig heeft.

```bash
./install.sh                 # maakt links in ~/.local/bin
sudo ./install.sh --prefix /usr/local/bin
```

```bash
dotserve                            # verstandige standaarden, print een adres om te joinen
dotserve --game res://games/arena   # een specifieke game
dotserve --port 27015 --web         # luistert ook naar browserclients
dotserve --restart                  # komt na een crash weer op
dotserve -- +sv_cheats 1 +map dm_arena
```

De eerste run schrijft een becommentarieerde `server.cfg` onder
`~/.config/dotserve`, genereert een RCON-wachtwoord en print het één keer. Elke
run daarna leest het bestand en raakt het nooit aan.

### Wat het doet en makkelijk wordt overgeslagen

**Het print het adres dat je een vriend kunt sturen**, inclusief een LAN-adres —
want "hij zegt dat hij gestart is en mijn vriend kan er niet in" is bijna altijd
een bindadres of een firewall, en het eerste dat helpt is weten op welk adres de
server werkelijk staat.

**Het weigert te starten met een raadbaar RCON-wachtwoord.** Een leeg wachtwoord
is prima en betekent dat de RCON-listener helemaal niet opengaat. Wat geweigerd
wordt is een tijdelijke waarde die is meegeleverd, uit een forumbericht gekopieerd
of in een sjabloon blijven staan.

**Het RCON-wachtwoord staat nooit op een opdrachtregel.** `server.cfg` wordt in
modus 600 aangemaakt voordat er iets in gaat. argv en de omgeving zijn op de meeste
systemen leesbaar door elk ander proces en belanden allebei in geplakte
foutrapporten — dezelfde reden waarom `DotConfig.sensitive_keys` ze weigert.

**Het overschrijft je `server.cfg` nooit.** Jouw bewerkingen *zijn* de configuratie
van de server.

### Opties die het waard zijn

| | |
| --- | --- |
| `--dry-run` | Print het commando dat het zou draaien, en stopt. |
| `--print-config` | Print de opgeloste configuratie, en stopt. |
| `--install-service [NAAM]` | Print een systemd-unit voor deze aanroep. |
| `--restart` | Herstart na een crash, met exponentiële backoff tot maximaal 60 seconden. |
| `--web` | Luistert ook naar browserclients, via WebSocket op de gamepoort zelf (TCP naast de UDP van de native clients). `--ws-port` wordt uit oudere unitbestanden geaccepteerd en genegeerd. |

De exitcodes hebben betekenis, zodat een supervisor een misconfiguratie van een
crash kan onderscheiden: `2` gebruik, `3` geen Godot, `4` geen project, `5` foute
config, `6` poort bezet. De gegenereerde systemd-unit noemt `3` tot en met `6` onder
`RestartPreventExitStatus`.

## TMC's servertool

`dot-server-deploy` is waar de collectie samenkomt tot iets dat een
servereigenaar met één commando start. Het is een Godot-project dat een
`dot-server` opstart, zijn configuratie uit `cfg/*.yml` leest, games uit
`content/` laadt en een browserclient serveert — en het **levert zelf geen game
mee**. Elke game, de lobby inbegrepen, is een ondertekend [dot-cloud](/learn/godot/addons/dot-cloud)-pakket dat de server vanaf een contentbron installeert en dat elke client bij het verbinden downloadt, zodat de client dezelfde build is ongeacht waarmee hij joint en een nieuwe game geen nieuwe client vraagt.

```bash
./setup.sh              # zoek een runtime, koppel de add-ons, schrijf ./server
./server                # start hem

docker compose up -d    # of hetzelfde in een container
```

Windows: `setup.bat` (een schil om `setup.ps1`), dan `.\server.ps1`.

<Callout type="info" title="Het heette vroeger `dot-server-setup-test`">
Hetzelfde project, een duidelijkere naam. Heb je een oudere checkout of een
oudere link, dan is het nu
[`modcommunity/dot-server-deploy`](https://github.com/modcommunity/dot-server-deploy).
</Callout>

### Drie scripts die makkelijk door elkaar gehaald worden

```bash
./play.sh               # een server en de browserclient, op de loopback
./play.sh playground    # start met een bepaalde game
./play.sh games         # wat er verder in content/ zit
./play.sh status
./play.sh down
```

`play.sh` is voor een ontwikkelaar die een regel heeft aangepast en het wil zien. Het print een link, bouwt de export opnieuw als die verouderd is, kopieert `embed.html` — de pagina die `?server=` uit de querystring haalt — naar de build, naast de door Godot gegenereerde `index.html`, en **meldt het wanneer een gepubliceerd pakket in `dist/` ouder is dan de gamerepository waaruit het is gebouwd**. De add-ons zijn gesymlinkt en altijd actueel; een pakket is een momentopname, dus het is het enige onderdeel dat veroudert, en een verouderd pakket koppelt netjes aan, draait, en is de game van vorige week.

`demo.sh` is de andere: vijf servers, nginx die TLS afhandelt, een publieke host,
een apart registreerbaar domein voor de game en een `sudo`-stap om een listener te
installeren. Goed om het platform aan iemand te laten zien, fout voor een
wijziging van één regel.

Geen van beide heeft iets te maken met `dev.sh`, de **website**, die helemaal geen
game start. De twee draaien naast elkaar.

<Callout type="warning" title="`play.sh` is alleen HTTP via de loopback">
Een HTTPS-pagina mag geen `ws://`-socket openen, dus die vorm werkt daar en nergens
anders. Een game *binnen* de site inframen is weer iets heel anders en heeft een
eigen registreerbaar domein nodig.
</Callout>

### Wat het een beheerder geeft

- **Eén commando om te starten.** `setup.sh` zoekt een Godot-runtime, koppelt de
  add-ons, schrijft een becommentarieerde `cfg/` en schrijft `./server`. Het
  overschrijft nooit een configuratiebestand dat er al is. RCON staat standaard
  aan, met een gegenereerd wachtwoord en alleen via loopback.
- **Configuratie in YAML**, per onderwerp opgesplitst — `server.yml`, `net.yml`,
  `rcon.yml`, `auth.yml`, `groups.yml`, `permissions.yml`, `vote.yml`, `content.yml`, `security.yml`, `log.yml`, `replay.yml`, `party.yml`, `matchmaking.yml`, `admin_menu.yml`, `loading.yml`. Alles wat
  `dot-server` als consolevariabele aanbiedt, kan daar onder zijn eigen naam in.
- **Rollen, geen flags.** Het rechtenmodel van dot-server bestaat bewust uit
  flags; `groups.yml` is de vertaling, zodat een beheerder
  `permissions: [kick, ban, mute]` onder een groep `admin` schrijft en een speler de flags krijgt.
- **Games die op naam worden geïnstalleerd.** `--games g2gfast,playground` (of `TMC_GAMES`) haalt bij het opstarten de descriptor en het pakket van elke game op bij de contentbron; `owner/name@version` noemt de gepubliceerde game van iemand anders. Een map onder `content/` met een `game.yml` erin is een game, en `changelevel` wisselt ertussen terwijl de spelers verbonden blijven.
- **De spelers kiezen de volgende game.** `!game_nominate`, `!game_rtv`, `!game_vote`, `!game_timeleft`, `!game_next` over de games in `content/`, via [`dot-vote`](/learn/godot/addons/dot-vote). Het voorvoegsel laat het kale `!rtv` over aan een game die over zijn eigen maps stemt. Elke game krijgt zijn eigen tijdslimiet in zijn eigen `game.yml`.
- **Een browserclient.** `./server export-web` bouwt hem; één export bedient elke
  server, omdat het adres uit `?server=` komt.

### De indeling, en waarom die in drieën splitst

```
cfg/       wat een beheerder bewerkt
content/   de games die hij aanbiedt — elk een game.yml; de game zelf is een pakket
data/      wat de server schrijft — from_yaml.cfg, admins.json, bans.json, audit.jsonl, de pakketcache
dist/      pakketten die vanaf deze machine zijn gepubliceerd, en de index waar servers van installeren
host/      het opstarten: YAML -> DotServer
client/    de clientschil. Bevat geen game; hij koppelt aan wat de server noemt
web/       de browserbuild, en de pagina die ?server= uit de URL haalt
```

`cfg/` is wat je bewerkt en `data/` is wat de server schrijft. `content/` wordt geschreven wanneer de server een game installeert, omdat de `game.yml` uit het ondertekende pakket komt; een machine die zijn eigen content meebrengt en niets installeert, kan het alleen-lezen koppelen.

<Callout type="info" title="`data/from_yaml.cfg` is wat jouw YAML geworden is">
Lees het wanneer een instelling genegeerd lijkt te worden. De YAML is een
**laag over het eigen vocabulaire van dot-server**, geen tweede vocabulaire, en
dat bestand is de vertaling.
</Callout>

Het is ook de plek waar elke game van de collectie als pakket wordt gepubliceerd en gewisseld terwijl er spelers op zitten, en de eerste plek waar iets uit deze collectie in een browser is geladen.
