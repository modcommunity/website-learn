[`dot-server`](/learn/godot/addons/dot-server) ist tief konfigurierbar — Cvars,
Flags, `server.cfg`, `autoexec.cfg`, `+command`-Argumente, RCON und geschichtete
Konfiguration aus Datei, Umgebung und argv. Was fehlte, war eine Haustür. Das
hier ist die Klingel.

## `dotserve`

Das einzige Stück der Sammlung, das kein Godot-Addon ist: ein Shell-Skript, das
`bash` und eine Godot-4.7+-Binärdatei braucht.

```bash
./install.sh                 # verlinkt nach ~/.local/bin
sudo ./install.sh --prefix /usr/local/bin
```

```bash
dotserve                            # sinnvolle Standardwerte, druckt eine Beitrittsadresse
dotserve --game res://games/arena   # ein bestimmtes Spiel
dotserve --port 27015 --web         # lauscht auch auf Browser-Clients
dotserve --restart                  # kommt nach einem Absturz wieder hoch
dotserve -- +sv_cheats 1 +map dm_arena
```

Der erste Lauf schreibt eine kommentierte `server.cfg` unter
`~/.config/dotserve`, erzeugt ein RCON-Passwort und druckt es einmal. Jeder
weitere Lauf liest die Datei und fasst sie nie an.

### Was es tut und leicht wegzulassen ist

**Es druckt die Adresse, die man einem Freund schicken kann**, samt einer
LAN-Adresse — denn „es sagt, es läuft, und mein Freund kommt nicht rein“ ist fast
immer eine Bindeadresse oder eine Firewall, und das Erste, was hilft, ist zu
wissen, auf welcher Adresse der Server tatsächlich liegt.

**Es weigert sich, mit einem erratbaren RCON-Passwort zu starten.** Ein leeres
ist in Ordnung und heißt, der RCON-Listener öffnet gar nicht erst. Abgelehnt wird
ein Platzhalter, der mit ausgeliefert wurde, aus einem Forum kopiert oder in
einer Vorlage stehen gelassen wurde.

**Das RCON-Passwort steht nie auf einer Kommandozeile.** `server.cfg` wird mit
Modus 600 angelegt, bevor irgendetwas hineinkommt. argv und die Umgebung sind für
jeden anderen Prozess auf der Maschine lesbar, und beide landen in eingefügten
Fehlerberichten — derselbe Grund, aus dem `DotConfig.sensitive_keys` sie ablehnt.

**Es überschreibt deine `server.cfg` nie.** Deine Änderungen *sind* die
Konfiguration des Servers.

### Optionen, die man kennen sollte

| | |
| --- | --- |
| `--dry-run` | Druckt den Befehl, den es ausführen würde, und beendet sich. |
| `--print-config` | Druckt die aufgelöste Konfiguration und beendet sich. |
| `--install-service [NAME]` | Druckt eine systemd-Unit für diesen Aufruf. |
| `--restart` | Startet nach einem Absturz neu, mit exponentiellem Backoff bis 60 Sekunden. |
| `--web` | Lauscht auch auf Browser-Clients, per WebSocket auf dem Spielport selbst (TCP neben dem UDP der nativen Clients). `--ws-port` wird aus älteren Unit-Dateien akzeptiert und ignoriert. |

Die Exit-Codes sind aussagekräftig, damit ein Supervisor eine Fehlkonfiguration
von einem Absturz unterscheiden kann: `2` Benutzung, `3` kein Godot, `4` kein
Projekt, `5` fehlerhafte Konfiguration, `6` Port belegt. Die erzeugte
systemd-Unit listet `3` bis `6` unter `RestartPreventExitStatus`.

## TMCs Serverwerkzeug

`dot-server-deploy` ist der Ort, an dem die Sammlung zu etwas
zusammenkommt, das eine Serverbetreiberin mit einem Befehl startet. Es ist ein
Godot-Projekt, das einen `dot-server` hochfährt, seine Konfiguration aus
`cfg/*.yml` liest, Spiele aus `content/` lädt und einen Browser-Client
ausliefert — und **es bringt kein eigenes Spiel mit**. Jedes Spiel, die Lobby eingeschlossen, ist ein signiertes [dot-cloud](/learn/godot/addons/dot-cloud)-Paket, das der Server von einem Content-Ursprung installiert und das jeder Client beim Verbinden herunterlädt; der Client ist also derselbe Build, was auch immer er betritt, und ein neues Spiel braucht keinen neuen.

```bash
./setup.sh              # Runtime finden, Addons verdrahten, ./server schreiben
./server                # starten

docker compose up -d    # oder dasselbe im Container
```

Windows: `setup.bat` (ein Wrapper für `setup.ps1`), dann `.\server.ps1`.

<Callout type="info" title="Es hieß früher `dot-server-setup-test`">
Dasselbe Projekt, klarerer Name. Wenn du einen älteren Checkout oder einen
älteren Link hast: Es ist jetzt
[`modcommunity/dot-server-deploy`](https://github.com/modcommunity/dot-server-deploy).
</Callout>

### Drei Skripte, die man leicht verwechselt

```bash
./play.sh               # ein Server und der Browser-Client, auf dem Loopback
./play.sh playground    # mit einem bestimmten Spiel starten
./play.sh games         # was sonst noch in content/ liegt
./play.sh status
./play.sh down
```

`play.sh` ist für Entwickler, die eine Zeile geändert haben und sie ansehen
wollen. Es gibt einen Link aus, baut den Export neu, wenn er veraltet ist,
kopiert `embed.html` — die Seite, die `?server=` aus dem Query-String liest — in den Build neben das von Godot erzeugte `index.html` und **sagt dir, wenn ein veröffentlichtes
Paket in `dist/` älter ist als das Spiel-Repository, aus dem es gebaut wurde**.
Die Addons sind per Symlink eingebunden und immer aktuell; ein Paket ist eine
Momentaufnahme und daher der einzige Teil, der veraltet, und ein veraltetes Paket
hängt sich sauber ein, läuft und ist das Spiel von letzter Woche.

`demo.sh` ist das andere: fünf Server, nginx, das TLS terminiert, ein
öffentlicher Host, eine eigene registrierbare Domain für das Spiel und ein
`sudo`-Schritt, um einen Listener zu installieren. Richtig, um jemandem die
Plattform zu zeigen, falsch für eine Ein-Zeilen-Änderung.

Keines von beiden hat etwas mit `dev.sh` zu tun, das die **Website** ist und
überhaupt kein Spiel startet. Die beiden laufen nebeneinander.

<Callout type="warning" title="`play.sh` ist nur Loopback-HTTP">
Eine HTTPS-Seite darf keinen `ws://`-Socket öffnen, also funktioniert diese Form
dort und nirgendwo sonst. Ein Spiel *in* der Seite einzubetten ist wieder etwas
anderes und braucht eine eigene registrierbare Domain.
</Callout>

### Was es einer Betreiberin gibt

- **Ein Befehl zum Starten.** `setup.sh` findet eine Godot-Runtime, verdrahtet
  die Addons, schreibt ein kommentiertes `cfg/` und schreibt `./server`. Eine
  bereits vorhandene Konfigurationsdatei wird nie überschrieben. RCON kommt
  eingeschaltet, mit erzeugtem Passwort und nur über Loopback.
- **Konfiguration in YAML**, nach Themen getrennt — `server.yml`, `net.yml`,
  `rcon.yml`, `auth.yml`, `groups.yml`, `permissions.yml`, `vote.yml`, `content.yml`, `security.yml`, `log.yml`, `replay.yml`, `party.yml`, `matchmaking.yml`, `admin_menu.yml`, `loading.yml`. Alles, was
  `dot-server` als Konsolenvariable anbietet, kann dort unter seinem eigenen
  Namen stehen.
- **Rollen statt Flags.** Das Rechtemodell von dot-server besteht bewusst aus
  Flags; `groups.yml` ist die Übersetzung, sodass eine Betreiberin
  `permissions: [kick, ban, mute]` unter einer Gruppe `admin` schreibt und ein Spieler die Flags bekommt.
- **Spiele werden per Name installiert.** `--games g2gfast,playground` (oder `TMC_GAMES`) holt beim Start Descriptor und Paket jedes Spiels vom Content-Ursprung; `owner/name@version` benennt das veröffentlichte Spiel von jemand anderem. Ein Verzeichnis unter `content/` mit einer `game.yml` darin ist ein Spiel, und `changelevel` wechselt zwischen ihnen, während die Spieler verbunden bleiben.
- **Die Spieler wählen das nächste Spiel.** `!game_nominate`, `!game_rtv`, `!game_vote`, `!game_timeleft`, `!game_next` über die Spiele in `content/`, per [`dot-vote`](/learn/godot/addons/dot-vote). Das Präfix überlässt das bloße `!rtv` einem Spiel, das über seine eigenen Karten abstimmt. Jedes Spiel hat sein eigenes Zeitlimit in seiner eigenen `game.yml`.
- **Ein Browser-Client.** `./server export-web` baut ihn; ein Export bedient jeden
  Server, weil die Adresse aus `?server=` kommt.

### Der Aufbau, und warum er sich dreiteilt

```
cfg/       was eine Betreiberin bearbeitet
content/   die Spiele, die er anbietet — je eine game.yml; das Spiel selbst ist ein Paket
data/      was der Server schreibt — from_yaml.cfg, admins.json, bans.json, audit.jsonl, der Paket-Cache
dist/      von dieser Maschine veröffentlichte Pakete und der Index, aus dem Server installieren
host/      der Start: YAML -> DotServer
client/    die Client-Hülle. Sie enthält kein Spiel; sie hängt ein, was der Server nennt
web/       der Browser-Build und die Seite, die ?server= aus der URL liest
```

`cfg/` bearbeitest du, und `data/` schreibt der Server. `content/` wird geschrieben, wenn der Server ein Spiel installiert, weil die `game.yml` aus dem signierten Paket kommt; eine Maschine, die ihren eigenen Inhalt mitbringt und nichts installiert, kann es nur lesbar einhängen.

<Callout type="info" title="`data/from_yaml.cfg` ist das, was aus deinem YAML wurde">
Lies sie, wenn eine Einstellung ignoriert zu werden scheint. Das YAML ist eine
**Oberfläche über dot-servers eigenem Vokabular**, kein zweites — und diese Datei
ist die Übersetzung.
</Callout>

Es ist außerdem der Ort, an dem jedes Spiel der Sammlung als Paket veröffentlicht und unter verbundenen Spielern gewechselt wird, und der erste Ort, an dem überhaupt etwas aus dieser Sammlung in einem Browser geladen wurde.
