[`dot-server`](/learn/godot/addons/dot-server) は非常に細かく設定できます。cvar、
フラグ、`server.cfg`、`autoexec.cfg`、`+command` 引数、RCON、そしてファイル・
環境変数・argv からの階層化設定。足りなかったのは玄関でした。これがその呼び鈴です。

## `dotserve`

コレクションの中で唯一、Godot アドオンでないもの。`bash` と Godot 4.7 以降の
バイナリーが必要なシェルスクリプトです。

```bash
./install.sh                 # ~/.local/bin にシンボリックリンクを張る
sudo ./install.sh --prefix /usr/local/bin
```

```bash
dotserve                            # 妥当な既定値で起動し、参加用アドレスを表示
dotserve --game res://games/arena   # 特定のゲームを指定
dotserve --port 27015 --web         # ブラウザークライアントも待ち受ける
dotserve --restart                  # クラッシュ後に復帰する
dotserve -- +sv_cheats 1 +map dm_arena
```

初回起動時に `~/.config/dotserve` へコメント付きの `server.cfg` を書き、RCON の
パスワードを生成して 1 度だけ表示します。それ以降の起動はそのファイルを読むだけで、
決して書き換えません。

### 省略されがちだけれど大事なこと

**友達に貼って渡せるアドレスを表示します。** LAN のアドレスも含めてです。
「起動したと言っているのに友達がつながらない」の原因はたいていバインドアドレスか
ファイアウォールで、まず助けになるのは「サーバーが実際にどのアドレスにいるか」を
知ることだからです。

**推測できる RCON パスワードでは起動を拒否します。** 空なら問題なく、その場合は
RCON のリスナー自体が開きません。拒否されるのは、そのまま出荷されてしまった
プレースホルダー、フォーラムからコピーしたもの、テンプレートに残ったままのもの
です。

**RCON のパスワードがコマンドラインに載ることはありません。** `server.cfg` は
中身を書き込む前にモード 600 で作られます。argv と環境変数はマシン上の他の
プロセスから読め、どちらも貼り付けられたバグ報告に紛れ込みます。
`DotConfig.sensitive_keys` がそれらを拒否するのと同じ理由です。

**あなたの `server.cfg` を上書きすることはありません。** あなたの編集内容こそが
サーバーの設定です。

### 知っておくとよいオプション

| | |
| --- | --- |
| `--dry-run` | 実行するはずのコマンドを表示して終了します。 |
| `--print-config` | 解決後の設定を表示して終了します。 |
| `--install-service [名前]` | この呼び出し用の systemd ユニットを表示します。 |
| `--restart` | クラッシュ後に再起動します。指数バックオフで最大 60 秒まで。 |
| `--web` / `--ws-port N` | ブラウザークライアントも待ち受けます。既定は `--port` + 1。 |

終了コードには意味があり、監視プロセスが設定ミスとクラッシュを区別できます。
`2` 使い方の誤り、`3` Godot が無い、`4` プロジェクトが無い、`5` 設定が不正、
`6` ポート使用中。生成される systemd ユニットは `3` から `6` を
`RestartPreventExitStatus` に列挙します。

## TMC のサーバーツール

`dot-server-deploy` は、このコレクションがサーバー運営者の「コマンド 1 つで
起動できるもの」にまとまる場所です。`dot-server` を起動し、設定を `cfg/*.yml` から
読み、`content/` からゲームを読み込み、ブラウザークライアントを配信する Godot
プロジェクトで、**自前のゲームは 1 本も持ちません**。ロビーを含むすべてのゲームは、署名された [dot-cloud](/learn/godot/addons/dot-cloud) パックで、サーバーがコンテンツの配信元からインストールし、すべてのクライアントが接続時にダウンロードします。そのためクライアントは何に参加しても同じビルドで、新しいゲームに新しいクライアントは要りません。

```bash
./setup.sh              # ランタイムを探し、アドオンを配線し、./server を書き出す
./server                # 起動する

docker compose up -d    # またはコンテナーで同じことを
```

Windows: `setup.bat`（`setup.ps1` のラッパー）のあとに `.\server.ps1`。

<Callout type="info" title="以前は `dot-server-setup-test` という名前でした">
同じプロジェクトで、名前が分かりやすくなっただけです。古いチェックアウトや古い
リンクをお持ちなら、現在は
[`modcommunity/dot-server-deploy`](https://github.com/modcommunity/dot-server-deploy)
です。
</Callout>

### 取り違えやすい 3 つのスクリプト

```bash
./play.sh               # サーバーとブラウザークライアントを、ループバックで
./play.sh playground    # 特定のゲームで開始する
./play.sh games         # content/ に他に何があるか
./play.sh status
./play.sh down
```

`play.sh` は、1 行変えたのでそれを見たい開発者のためのものです。リンクを表示し、
エクスポートが古ければ再ビルドし、`embed.html`（`?server=` をクエリ文字列から受け取るページ）を Godot が生成した `index.html` の隣にビルドへコピーし、さらに **`dist/` にある公開済み
パックが、その元になったゲームリポジトリより古いときは知らせてくれます**。アドオンは
シンボリックリンクで常に最新ですが、パックはスナップショットなので、古くなるのは
そこだけです。そして古いパックは問題なくマウントされ、動き、先週のゲームになります。

`demo.sh` はもう一方です。サーバー 5 台、TLS を終端する nginx、公開ホスト、ゲーム用の
別の登録可能ドメイン、そしてリスナーをインストールするための `sudo` の手順。誰かに
プラットフォームを見せるには適していますが、1 行の変更には不向きです。

どちらも `dev.sh` とは無関係です。`dev.sh` は**ウェブサイト**で、ゲームは一切起動
しません。両者は並べて動かせます。

<Callout type="warning" title="`play.sh` はループバックの HTTP 専用です">
HTTPS のページは `ws://` ソケットを開けないため、この形はそこでしか動きません。
ゲームをサイトの*中*にフレームで埋め込むのはまた別の話で、専用の登録可能ドメインが
必要です。
</Callout>

### 運営者に与えるもの

- **起動はコマンド 1 つ。** `setup.sh` が Godot ランタイムを探し、アドオンを配線し、
  コメント付きの `cfg/` と `./server` を書き出します。すでにある設定ファイルを
  上書きすることは決してありません。RCON は有効の状態で出荷されます。パスワードは自動生成され、ループバックからのみ接続できます。
- **設定は YAML**、テーマごとに分割されています。`server.yml`、`net.yml`、
  `rcon.yml`、`auth.yml`、`groups.yml`、`vote.yml`、`permissions.yml`、`security.yml`、`log.yml`。
  `dot-server` がコンソール変数として公開しているものは、すべてそのままの名前で
  書けます。
- **フラグではなくロール。** dot-server の権限モデルは意図的にフラグですが、
  `groups.yml` がその翻訳です。運営者は `admin` グループの下に `permissions: [kick, ban, mute]` と書き、
  プレイヤーにはフラグが付きます。
- **ゲームは名前でインストールされます。** `--games g2gfast,playground`（または
  `TMC_GAMES`）で、起動時にコンテンツの配信元から各ゲームのディスクリプターとパックを
  取得します。`owner/name@version` は他の誰かが公開したゲームを指します。`content/` の
  下にある `game.yml` を含むディレクトリーが 1 本のゲームで、`changelevel` は
  プレイヤーを接続したまま切り替えます。
- **次に何を遊ぶかはプレイヤーが決めます。** `content/` のゲームに対して
  `!game_nominate`、`!game_rtv`、`!game_vote`、`!game_timeleft`、`!game_next`。
  [`dot-vote`](/learn/godot/addons/dot-vote) 経由です。接頭辞があるので、素の `!rtv` は
  自分のマップを投票にかけるゲームに残されます。各ゲームは自分の `game.yml` に自分の
  時間制限を持ちます。
- **ブラウザークライアント。** `./server export-web` でビルドします。アドレスは
  `?server=` から来るので、1 回のエクスポートですべてのサーバーに使えます。

### 構成と、3 つに分かれている理由

```
cfg/       運営者が編集するもの
content/   提供するゲーム — それぞれに game.yml。ゲーム本体はパック
data/      サーバーが書き込むもの — from_yaml.cfg、admins.json、bans.json、audit.jsonl、パックのキャッシュ
dist/      このマシンから公開したパックと、サーバーがインストール元にする索引
host/      起動処理: YAML -> DotServer
client/    クライアントの外枠。ゲームを含まず、サーバーが指名したものをマウントする
web/       ブラウザー用ビルドと、URL から ?server= を読むページ
```

`cfg/` は編集するもの、`data/` はサーバーが書き込むものです。`content/` はサーバーがゲームをインストールするときに書き込まれます。`game.yml` は署名されたパックから出てくるからです。自前のコンテンツを持ち何もインストールしないマシンなら、読み取り専用でマウントできます。

<Callout type="info" title="`data/from_yaml.cfg` はあなたの YAML が変換された結果です">
設定が無視されているように見えたら、これを読んでください。YAML は
**dot-server 自身の語彙の上にかぶせた表層**であって、第 2 の語彙ではありません。
このファイルがその翻訳結果です。
</Callout>

ここは、コレクションのすべてのゲームがパックとして公開され、プレイヤーが接続したまま切り替えられる場所であり、このコレクションの何かが初めてブラウザーで読み込まれた場所でもあります。
