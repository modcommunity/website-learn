服务器给客户端一份清单；客户端下载自己缺的部分、校验它、然后挂载——在 Windows、
macOS、Linux、Android、iOS 以及浏览器上都是如此。

```gdscript
var cloud := DotCloudClient.new()
add_child(cloud)

cloud.config = DotCloudConfig.new()
cloud.config.trusted_keys = {"default": PUBLIC_KEY_PEM}
await cloud.start()

cloud.phase_changed.connect(func(_p, text): status_label.text = text)
cloud.progress_changed.connect(func(p): bar.value = p.fraction * 100.0)

var res := await cloud.acquire("https://cdn.example.com/dm_arena/manifest.json")
if res.ok:
    get_tree().change_scene_to_file(res.value)
```

发布走的是一个无界面 CLI，产出一个**静态目录**——一份 `manifest.json` 加一棵
`objects/` 树——任何 web 服务器或 CDN 都能零配置地把它托管起来：

```bash
godot --headless --path . --script addons/dot_cloud/publish/dot_cloud_cli.gd -- \
    keygen --private keys/content.key --public keys/content.pub

godot --headless --path . --script addons/dot_cloud/publish/dot_cloud_cli.gd -- \
    publish --source content/dm_arena --out dist/dm_arena \
    --id dm_arena --version 1.2.0 --entry arena.tscn --key keys/content.key
```

导入资源的源文件（导入产物背后的 `.glb` 或 `.png`）默认不放进包里，因为包已经带有导入产物；`--with-sources` 可以把它加回来。不在源目录下的文件，例如由构建步骤派生的文件，通过 `DotCloudPublisher.extra_files`（包内路径到文件）加入，而不是写进别人的检出目录。

## 塑造了一切的两条约束

**Godot 无法卸载已挂载的资源包。** 不是慢，也不是有变通办法——这个 API 根本不存在。
于是每一份内容都拿到自己的带版本路径 `res://<root>/<content_id>/<version>/`，从而
永远不需要替换任何东西。“卸载”意味着放开引用，而不是收回文件表。正是这一个事实，才
让运行时切换游戏成为可能。

**未签名的内容等于远程代码执行。** Godot 的资源包里可以放脚本，所以是清单决定了什么
会被执行。`require_signed_manifests` 默认开启，而且在没有可信密钥时配置会直接拒绝
通过校验。你可以为局域网或自有服务器关掉它；它每次都会警告。

## 它做的事

- **按内容寻址的缓存。** 文件以自身的 SHA-256 存放，因此两个共用某个资源的游戏只
  下载一次，重新发布也只会重新下载变更过的部分。
- **可续传的并行下载。** 镜像切换、HTTP range 续传、按来源的熔断、带宽限速，以及
  诚实的进度和预计时间。
- **三种来源。** HTTP/CDN、本地目录（开发、局域网、随包内容），以及对于没有 web
  主机的服务器，走游戏连接的带内传输。
- **配额意识。** 浏览器的存储估算、移动端上限，以及绝不淘汰正在使用中的内容的
  最近最少使用淘汰策略。

## 挂载时检查什么

在下载和挂载之间，资源包要通过四条规则，每一条都来自有人实测过的失败：

- **先读它的 `requires.json`。** 资源包里的脚本是针对宿主的插件编译的，所以需要更新插件的
  资源包过去会在加载途中解析失败。现在它在任何脚本加载之前就被拒绝，提示是
  *“This game needs dot-net API level 3 or newer; this build has level 2.”*——见
  [插件 API 级别](/learn/godot/addons/dot-core#addon-api-levels-dotaddonapi)。
  `host_role` 指明是哪一侧。
- **内容 id 可以带上所有者：`<owner>/<name>`。** 两半里都不可能出现 `/`，所以作用域为
  `alice/*` 的密钥是精确的——压扁成 `alice_bob` 的写法分不清 `alice` + `bob_x` 和
  `alice_bob` + `x`。每一段都必须是 slug；不带所有者的 id（每个第一方资源包都是）仍然通过校验。
- **一个 id 不能指两样东西。** 同一个 `content_id@version` 若有来自不同发布者的第二份清单，
  会以 `CODE_CONFLICT` 被拒绝，而不是拿到第一份的挂载——资源包里可以有脚本，而“第一份”
  是别人的代码。从网络上重新读到的相同清单仍然是一次廉价的空操作。
- **挂载的资源包注册自己的 uid，且不得占用别人的。** 导入的资产（`.glb`、`.png`）通过 UID
  引用它的同伴，而 UID 在被挂载到别处后无法保持；挂载器会把每个 UID 指向挂载后的副本。
  宿主已持有的 UID 会被拒绝并上报，否则构建里每个 `load("uid://…")` 都可能被重新指向下载来的内容。

<Callout type="warning" title="导入产物放在 `_imported/` 下发布，绝不放在 `.godot/` 下">
发布的资源包带有引擎的导入产物，它们过去放在真实路径 `.godot/imported/` 下。Linux 读回来
完全没问题；**web 导出读不了**，整个游戏在浏览器里拒绝启动。现在产物放在 `_imported/` 下发布，
每个 `.import` 标记都被改写为指向产物落地的位置。否则，挂载的资源包里缺失的美术只会表现为
警告——资源包校验通过、挂载成功、加载完成，只是缺了贴图。
</Callout>

## Provides、会话标签与 Workshop

包可以声明自己提供什么。包源根目录下的 `provides.json`（地图、武器、道具、NPC、音效、脚本等类型，每类带条目，也可以带适用的游戏）由发布工具校验，并作为 `provides` 签入清单。挂载这样的包时，客户端会把它的条目登记到 `DotContentIndex`（在 `dot-core` 中），地图菜单或生成菜单因此无需提及任何包路径就能找到已交付的内容。游戏包声明一个 `accepts` 块，列出它接受的类型；没有该块的游戏不接受任何订阅。

发布工具还会在 `provides` 中设置 `runs_code`，由 `DotCloudScriptScan` 根据文件计算，而不是采用作者的说法。它是给诚实的包用的标签，不是沙箱。

索引中的每个包都带有它被挂载时所属的会话，`solo` 或 `online`，只有当前会话的条目可见。`DotCloudClient.session_tag`（默认 `online`）标记 `ensure()` 和 `acquire()` 所挂载的内容，`ensure_for_session(content_id, version, session, source, options)` 则显式传入标签和挂载选项。订阅挂载使用 `uid_policy = "add_only"`，因此下载的包永远不能改指游戏已持有的 UID，来自订阅的 `addon` 覆盖层会以 `CODE_FORBIDDEN` 被拒绝。

`DotCloudWorkshop`（注册名 `dot_workshop`）是单人游戏的同步客户端：它向网站询问玩家订阅的包，为单人启动下载并挂载，并且绝不会在联机会话中运行。如果挂载过会执行代码的包，加入联机服务器时会先重启进程，因为常驻脚本无法卸载。它的 `DotCloudWorkshopConfig` 设置了 `workshop_script_packs`（`never`、`approved` 或 `any`；默认 `approved`）、`workshop_metered`（`ask`、`allow`、`never`）和 `workshop_key_ids`（订阅必须携带的签名密钥，刻意与服务器内容所信任的密钥分开）等。宿主提供 `token_fn`（已登录玩家的 bearer）和 `ask_fn`（“下载 N MB？”的询问）。

## 游戏从哪里接入

<Params>
  <Param name="DotCloudSource 的子类">
    `source_name()`、`is_supported()`、`can_serve(manifest)`、`fetch(...)`。
    随包提供三种——`DotCloudSourceHttp`、`DotCloudSourceLocal`、
    `DotCloudSourceNetchan`——第四种是你的：一个 torrent、一个平台专属 CDN、一个
    签名 S3 链接的签发器。

    `fetch` **必须**写入该文件哈希对应的 `DotCloudStore.partial_path`，能续传时
    从 `partial_size` 续，并且通过 `commit_partial` 收尾。那是唯一校验哈希的地方，
    而直接往对象目录里写，正是未校验内容被挂载的途径。
  </Param>
  <Param name="can_serve() 与 is_supported() 的区别">
    这个区分是值回票价的。一个来源可以完全健康，却依然没有办法拿到*这一份*清单——
    比如一个没有配 `base_urls` 的 HTTP 来源，碰上一份不带镜像的清单。从
    `can_serve` 返回失败的意思是“这份清单请跳过我，原因如下”，而且**不会**记到
    熔断器头上。
  </Param>
  <Param name="priority" type="int">
    每个来源上都有。数值越小越先尝试；带内的兜底来源被刻意排在最后。
  </Param>
  <Param name="DotCloudConfig">
    `trusted_keys`、`require_signed_manifests`、`cache_bytes`、
    `mobile_cache_bytes`、`web_quota_fraction`、`parallel_downloads`、
    `max_attempts_per_file`、`throttle_bytes_per_sec`、`file_timeout_sec`、`cache_dir`、
    `verify_before_mount`、`verify_cache_on_start`、`resume_downloads`、`enforce_mount_prefix`。像所有 `DotConfig` 一样分层。
  </Param>
  <Param name="manifest_url_template / manifest_url_fallbacks" type="DotCloudClient">
    向哪里请求清单，由基础 URL、id 和版本拼出。默认是 `{base}/{id}/{version}/manifest.json`，也就是站点发布的形式；`manifest_url_fallbacks` 列出在它之后、按每个基础地址依次尝试的其他形式，因为同一个源上可能存放着以两种布局发布的资源包，而重新发布全部资源包并不是启动的前提。
  </Param>
  <Param name="信号">
    在 `DotCloudClient` 上：`phase_changed`、`progress_changed`、`content_ready`、`content_released`、`failed`。逐文件的细节在下载器上：`file_finished`、`sync_finished`。
  </Param>
</Params>

## 其他插件期待的那套内容接口

注册一个 `DotCloudClient`，它就会以 `dot_cloud_client` 这个名字发布自己。
`dot-map` 的加载器和 `dot-server` 的切换游戏都通过这个名字找到它，并调用：

```gdscript
ensure(content_id: StringName, version: String = "", groups := PackedStringArray(), manifest_url := "") -> DotResult
is_mounted(content_id: StringName, version: String = "") -> bool
```

大多数插件是通过 [`dot-core`](/learn/godot/addons/dot-core#downloadable-content-dotcontent)
里的 `DotContent` 来调用它们的——那是唯一共享的调用方，也正是靠它，点名了内容的形象部件、
道具、NPC、载具和物品现在才真的会去获取它。

<Callout type="warning" title="没有云端客户端本身也是一种合法配置">
每一处调用点都把“没有 `dot_cloud_client`”理解为“这套部署把内容打进了构建里”——对
你自己的游戏来说这是一种合法的选择，因此它和一个没能注册上的客户端是无法区分的。TMC 自己的部署在构建里根本不带任何内容：每个游戏、每张导入的地图和大厅，都是由这个插件获取的资源包。当一张
可分发的地图或一个可分发的游戏悄无声息地什么都不做时，先去看注册表。
</Callout>
