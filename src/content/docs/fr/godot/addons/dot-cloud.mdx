Un serveur remet un manifeste à un client ; le client télécharge ce qui lui
manque, le vérifie et le monte — sur Windows, macOS, Linux, Android, iOS et dans
le navigateur.

```gdscript
var cloud := DotCloudClient.new()
add_child(cloud)

cloud.config = DotCloudConfig.new()
cloud.config.trusted_keys = {"default": PUBLIC_KEY_PEM}
await cloud.start()

cloud.phase_changed.connect(func(_p, text): status_label.text = text)
cloud.progress_changed.connect(func(p): bar.value = p.fraction * 100.0)

var res := await cloud.acquire("https://cdn.example.com/dm_arena/manifest.json")
if res.ok:
    get_tree().change_scene_to_file(res.value)
```

La publication passe par une CLI sans interface qui produit un **dossier
statique** — un `manifest.json` plus une arborescence `objects/` — que n'importe
quel serveur web ou CDN sert sans configuration :

```bash
godot --headless --path . --script addons/dot_cloud/publish/dot_cloud_cli.gd -- \
    keygen --private keys/content.key --public keys/content.pub

godot --headless --path . --script addons/dot_cloud/publish/dot_cloud_cli.gd -- \
    publish --source content/dm_arena --out dist/dm_arena \
    --id dm_arena --version 1.2.0 --entry arena.tscn --key keys/content.key
```

## Les deux contraintes qui ont tout façonné

**Godot ne peut pas démonter un pack de ressources.** Ni lentement, ni par une
astuce : l'API n'existe pas. Chaque ensemble de contenu reçoit donc son propre
chemin versionné, `res://<root>/<content_id>/<version>/`, et rien n'a jamais
besoin d'être remplacé. « Décharger » veut dire lâcher des références, pas
récupérer la table des fichiers. Ce seul fait est ce qui rend possible le
changement de jeu à l'exécution.

**Du contenu non signé, c'est de l'exécution de code à distance.** Un pack Godot
peut contenir des scripts, donc un manifeste décide de ce qui s'exécute.
`require_signed_manifests` est activé par défaut et la configuration refuse de se
valider sans clé de confiance. Vous pouvez le désactiver pour un réseau local ou
un serveur maison ; il vous avertira à chaque fois.

## Ce qu'il fait

- **Cache adressé par contenu.** Les fichiers sont rangés sous leur SHA-256, donc
  deux jeux qui partagent un asset ne le téléchargent qu'une fois, et republier
  ne re-télécharge que ce qui a changé.
- **Téléchargements parallèles reprenables.** Bascule entre miroirs, reprise par
  plages HTTP, coupe-circuit par source, limitation de débit, et progression et
  estimation honnêtes.
- **Trois sources.** HTTP/CDN, un dossier local (développement, réseau local,
  contenu embarqué), et en bande via la connexion de jeu pour un serveur sans
  hébergement web.
- **Conscience des quotas.** Estimations de stockage du navigateur, plafonds
  mobiles, et éviction du moins récemment utilisé qui n'évince jamais du contenu
  en cours d'usage.

## Ce que vérifie le montage

Entre le téléchargement et le montage, un pack est soumis à quatre règles qui
viennent chacune d'un échec que quelqu'un a mesuré :

- **Son `requires.json` est lu en premier.** Les scripts d'un pack compilent
  contre les modules de l'hôte, si bien qu'un pack exigeant un module plus récent
  échouait autrefois à l'analyse en plein chargement. Il est désormais refusé avant
  qu'un script ne charge, avec *« Ce jeu a besoin de dot-net API level 3 ou plus ;
  ce build est au niveau 2. »* — voir
  [niveaux d'API des modules](/learn/godot/addons/dot-core#addon-api-levels-dotaddonapi).
  `host_role` nomme le côté.
- **Un identifiant de contenu peut nommer son propriétaire : `<owner>/<name>`.**
  `/` ne peut apparaître dans aucune des deux moitiés, donc une clé bornée à
  `alice/*` est exacte — un `alice_bob` aplati ne pourrait pas distinguer `alice` +
  `bob_x` de `alice_bob` + `x`. Chaque segment doit être un slug ; un identifiant nu,
  ce que sont tous les packs first-party, est toujours valide.
- **Un identifiant ne peut pas signifier deux choses.** Un second manifeste pour le
  même `content_id@version` venant d'un autre éditeur est refusé avec
  `CODE_CONFLICT` plutôt que de recevoir le montage du premier — un pack peut
  contenir des scripts, et « celui du premier » est le code de quelqu'un d'autre. Un
  manifeste identique relu sur le réseau reste un no-op bon marché.
- **Un pack monté enregistre ses propres uids, et ne peut prendre ceux de
  personne d'autre.** Un asset importé (un `.glb`, un `.png`) désigne ses voisins
  par UID, ce qui ne survit pas à un montage ailleurs ; le monteur repointe chaque
  UID vers la copie montée. Un UID que l'hôte détient déjà est refusé et signalé,
  faute de quoi chaque `load("uid://…")` de la build pourrait être repointé vers du
  contenu téléchargé.

<Callout type="warning" title="Les sorties importées sont livrées sous `_imported/`, jamais `.godot/`">
Un pack publié transporte les sorties importées du moteur, et elles se trouvaient
autrefois à leur vrai chemin, `.godot/imported/`. Linux les relit parfaitement ;
**un export web ne le peut pas**, et tout le jeu refusait de démarrer dans le
navigateur. Les sorties sont désormais livrées sous `_imported/`, chaque marqueur
`.import` étant réécrit pour nommer l'endroit où la sortie a atterri. Sinon, des
visuels manquants dans un pack monté ne se manifestent que par des avertissements —
le pack se vérifie, se monte et se charge sans ses textures.
</Callout>

## Où un jeu se branche

<Params>
  <Param name="Sous-classe de DotCloudSource">
    `source_name()`, `is_supported()`, `can_serve(manifest)`, `fetch(...)`. Trois
    sont livrées — `DotCloudSourceHttp`, `DotCloudSourceLocal`,
    `DotCloudSourceNetchan` — et la quatrième est la vôtre : un torrent, un CDN
    propre à une plateforme, un générateur d'URL S3 signées.

    Un `fetch` **doit** écrire dans `DotCloudStore.partial_path` pour le hachage
    du fichier, reprendre depuis `partial_size` quand il le peut, et finir par
    `commit_partial`. C'est le seul endroit où le hachage est vérifié, et écrire
    directement dans le répertoire d'objets est exactement la façon dont du
    contenu non vérifié se retrouve monté.
  </Param>
  <Param name="can_serve() face à is_supported()">
    La distinction mérite sa place. Une source peut être en parfaite santé et
    n'avoir malgré tout aucun moyen d'atteindre *ce* manifeste-là — une source
    HTTP sans `base_urls` face à un manifeste sans miroirs. Renvoyer un échec
    depuis `can_serve` veut dire « ignore-moi pour ce manifeste, et voici
    pourquoi », et n'est **pas** compté contre le coupe-circuit.
  </Param>
  <Param name="priority" type="int">
    Sur chaque source. Le plus bas passe en premier ; le repli en bande est
    délibérément dernier.
  </Param>
  <Param name="DotCloudConfig">
    `trusted_keys`, `require_signed_manifests`, `cache_bytes`,
    `mobile_cache_bytes`, `web_quota_fraction`, `parallel_downloads`,
    `max_attempts_per_file`, `throttle_bytes_per_sec`, `file_timeout_sec`, `cache_dir`,
    `verify_before_mount`, `verify_cache_on_start`, `resume_downloads`,
    `enforce_mount_prefix`. En couches comme tout `DotConfig`.
  </Param>
  <Param name="manifest_url_template / manifest_url_fallbacks" type="DotCloudClient">
    Où un manifeste est demandé, à partir d'une URL de base, d'un identifiant et
    d'une version. Par défaut `{base}/{id}/{version}/manifest.json`, ce que publie
    le site ; `manifest_url_fallbacks` liste d'autres formes essayées ensuite, par
    base, parce qu'une même origine peut contenir des packs publiés sous deux
    dispositions et les republier tous n'est pas un préalable pour démarrer.
  </Param>
  <Param name="Signaux">
    Sur `DotCloudClient` : `phase_changed`, `progress_changed`, `content_ready`,
    `content_released`, `failed`. Le détail par fichier est sur le téléchargeur :
    `file_finished`, `sync_finished`.
  </Param>
</Params>

## L'interface de contenu qu'attendent les autres modules

Enregistrez un `DotCloudClient` et il se publie sous `dot_cloud_client`. Le
chargeur de `dot-map` et le changement de jeu de `dot-server` l'atteignent par ce
nom et appellent :

```gdscript
ensure(content_id: StringName, version: String = "", groups := PackedStringArray(), manifest_url := "") -> DotResult
is_mounted(content_id: StringName, version: String = "") -> bool
```

La plupart des modules les atteignent par `DotContent` dans
[`dot-core`](/learn/godot/addons/dot-core#downloadable-content-dotcontent), l'appelant
partagé unique — ce qui fait que les parties d'avatar, les props, les PNJ, les
véhicules et les objets qui nomment un contenu le récupèrent désormais
réellement.

<Callout type="warning" title="Un client de contenu absent est une configuration légitime">
Tous les appelants traitent « pas de `dot_cloud_client` » comme « ce déploiement
embarque son contenu dans la build » — ce qui est un choix légitime pour votre
propre jeu, et donc indiscernable d'un client qui ne s'est pas enregistré. Le
déploiement de TMC n'embarque aucun contenu dans sa build : chaque jeu, chaque
carte importée et le salon sont des packs que ce module récupère. Quand une
carte ou un jeu livré ne fait silencieusement rien, regardez d'abord le registre.
</Callout>
